# پلی‌بوک — ورود داده فروش (Sales Import)

> داده فروش، ورودی امتیاز عملکرد است. یک import بد = امتیاز غلط = بی‌اعتمادی به کل محصول.

---

## ۱. چرخه عمر Import

```
created → uploaded → validated → processing → completed
                         ↓            ↓
                      rejected      failed
```

هر import این‌ها را دارد:

- `id`, `source_id`, `file_name`, `file_fingerprint` (hash), `uploaded_by`, `uploaded_at`
- `status`, `row_count`, `valid_count`, `invalid_count`, `created_at`, `finished_at`
- خطاهای ردیفی جدا: `row_number`, `raw_row`, `error_code`, `message`

---

## ۲. قرارداد ورودی (اولیه — `OPEN` تا دریافت فایل واقعی)

| فیلد | نوع | الزامی | توضیح |
|---|---|---|---|
| `external_id` | string | ✅ | شناسه یکتای رکورد در سیستم مبدأ |
| `user_external_id` | string | ✅ | شناسه ویزیتور (mapping صریح) |
| `sale_date` | date | ✅ | تاریخ فروش (timezone مشخص) |
| `sku_code` | string | ✅ | کد محصول |
| `quantity` | numeric | ✅ | مقدار |
| `amount` | numeric | ✅ | مبلغ |
| `customer_external_id` | string | ❌ | شناسه مشتری |
| `branch_code` | string | ❌ | شعبه/مرکز |

قواعد:

- **شناسه یکتا** = `external_id` (در سطح منبع). اگر مبدأ شناسه یکتا ندارد، `OPEN` و راه‌حل موقت مستند.
- Mapping شناسه خارجی → کاربر داخلی صریح و قابل گزارش است، نه حدس.
- فایل خام یا fingerprint طبق سیاست نگهداری حفظ می‌شود.

---

## ۳. اعتبارسنجی در دو سطح

**سطح فایل:** نوع/حجم/encoding/ستون‌های الزامی/سرصفحه/تعداد ردیف/تاریخ خالی.

**سطح رکورد:** نوع داده، مقدار منفی، تاریخ آینده، کاربر ناموجود، SKU نامعتبر، تکراری در همان فایل.

نتیجه: `validated` با گزارش کامل، یا `rejected` با دلیل فایل‌سطح. رکورد نامعتبر **کل فایل را رد نمی‌کند** (مگر سیاست خلافش را بگوید)؛ اما امتیاز نمی‌گیرد و گزارش می‌شود.

---

## ۴. ضدتکرار

سه سناریو که باید صریح باشند:

| سناریو | سیاست پیشنهادی | وضعیت |
|---|---|---|
| همان فایل دوباره | fingerprint یکسان → رد با پیام واضح | `PROPOSED` |
| همان رکورد در import دیگر | `(source_id, external_id)` یکتا → skip + گزارش | `PROPOSED` |
| اصلاح رکورد قبلی | نسخه جدید رکورد + رویداد اصلاحی امتیاز | `OPEN` (سیاست کارفرما) |
| برگشت/کنسلی فروش | رویداد معکوس، بدون حذف تاریخچه | `OPEN` |

هیچ‌کدام «خودکار و خاموش» حل نمی‌شوند؛ هر رفتار باید در گزارش و سند دیده شود.

---

## ۵. پردازش

- batch و idempotent؛ اجرای دوباره همان `import_id` نباید امتیاز تکراری بسازد.
- هر رکورد معتبر → امتیاز فروش از قانون فعال (نسخه بر اساس `sale_date`/زمان پردازش — این انتخاب `OPEN` است و باید ثبت شود).
- خطای یک رکورد، بقیه را متوقف نمی‌کند؛ شمارش و گزارش می‌شود.
- پیشرفت و وضعیت قابل مشاهده در پنل.

---

## ۶. Reconciliation

پس از پردازش، این اعداد باید با مبدأ قابل تطبیق باشند:

```
rows_in_file == valid_count + invalid_count
sum(points created) == sum(expected per rule)     # با گزارش اختلاف
sum(amount) == sum(amount in source report)       # در صورت وجود
```

اختلاف = هشدار، نه سکوت.

---

## ۷. چک‌لیست برش

- [ ] آپلود + fingerprint + وضعیت
- [ ] اعتبارسنجی فایل و رکورد + گزارش خطا با شماره ردیف
- [ ] dedupe با unique constraint
- [ ] پردازش batch + idempotency
- [ ] امتیاز از قانون نسخه‌دار
- [ ] reconciliation + گزارش
- [ ] صفحه پنل: لیست importها، جزئیات، خطاها
- [ ] تست: فایل سالم، فایل با ردیف خراب، فایل تکراری، اجرای دوباره

---

## ۸. ضدالگوها

- import بدون شناسه و بدون وضعیت.
- رد کل فایل به‌خاطر یک ردیف خراب بدون گزارش.
- mapping حدسی شناسه ویزیتور.
- امتیازدهی در لحظه آپلود، قبل از validate.
- اجرای دوباره و امتیاز دوم.
